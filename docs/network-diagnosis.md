# GitHub 连接诊断与方案（Owner 委托 · 2026-09-06）

> 结论先行：直连失败的原因是**间歇性 SNI 干扰**（GFW 行为特征），不是 DNS 污染也不是本机配置错误。当前最优方案 = **保留本地代理，但把作用域收窄到仅 github.com**（已实施）。

## 诊断过程（实测数据）

| 检查项 | 结果 | 判定 |
|---|---|---|
| DNS 解析 | `github.com → 20.205.243.166`（GitHub 正版 IP，教育网 IPv6 DNS） | ✅ 无污染 |
| TCP/TLS 直连（单次） | HTTP 200，connect 0.10s，total 0.73s | 表面正常 |
| TCP/TLS 直连（**连续 5 次**） | `000 000 000 200 000` —— **4/5 失败** | ⚠️ 间歇性干扰：TLS 握手阶段被 RST，特征是"有时通" |
| 经代理 127.0.0.1:7897 | HTTP 200 稳定 | ✅ 可靠 |
| git ls-remote（原配置） | 成功（原配置把整个仓库的所有远端都走代理） | ✅ 但作用域过宽 |

**为什么"有时通"**：SNI（服务器名称指示）字段在 TLS ClientHello 里明文可见，干扰设备基于它选择性重置连接——重置窗口外就能成功。这解释了早期"间歇性直连故障"（event seq 33）和本次单次 200、连续 4/5 失败的矛盾现象。

## 方案对比

| 方案 | 可靠性 | 成本 | 结论 |
|---|---|---|---|
| 裸直连 | 间歇失败（4/5） | 0 | ❌ 不可作为唯一路径 |
| **仓库级代理，仅 github.com（已实施）** | 稳定 | 一行配置 | ✅ **当前方案** |
| SSH over 443（`ssh.github.com:443`） | 通常更抗干扰（非 SNI 特征） | 需生成/上传 SSH key | 备选，若代理客户端不可用时切换 |
| 镜像/加速器（ghproxy 类） | 不稳定且引入第三方信任 | — | ❌ 不采用：不可信中间人对 git 对象是安全风险 |

## 已实施的配置

```bash
git config http.https://github.com.proxy http://127.0.0.1:7897  # 仅 github.com 走代理
git config --unset http.proxy                                   # 其余远端不受影响
```

依赖说明：`127.0.0.1:7897` 是 Owner 本机的代理客户端（Clash 系）。**若它没启动，git 操作会失败**——届时临时改用：`git -c http.https://github.com.proxy= fetch`（赌直连窗口），或启动代理客户端。

## 免踩坑清单（Windows + 网络）

- `git ls-remote`/`push` 卡住无输出：多半是代理客户端没开，先 `curl -x http://127.0.0.1:7897 https://github.com` 验证。
- LNK1104 "无法打开 exe"：上次运行的 mirage_m0.exe 没关（本 run 实测踩过）——`taskkill //IM mirage_m0.exe //F`。
- 终端中文乱码（上面诊断输出就是）：Git Bash 管道下的 UTF-8 显示问题，不影响数据。
